# P0 需求变更流程

## 1. 适用范围

P0 签字后，任何新增功能、删除功能、GraphQL 契约变化、业务规则变化、数据破坏性迁移、阶段门禁降低或技术路线变化都必须提交变更单。缺陷修复如果改变用户可观察行为，也按变更处理。

## 2. 变更单最小内容

```text
变更 ID：CR-YYYYMMDD-NNN
提出人/日期：
业务问题与预期结果：
是否影响本轮范围：新增 / 删除 / 规则变化 / 技术变化
影响的 GraphQL operation / Schema：
影响的数据模型与 migration：
安全、隐私、性能和运维影响：
前端、后端、QA 工作量：
排期与里程碑影响：
兼容、灰度与回滚方案：
备选方案：
评审结论：批准 / 拒绝 / 延期
批准人和日期：
关联 ADR、测试和文档：
```

## 3. 流程

1. 提出人创建变更单，不得直接把需求插入开发分支。
2. BE、FE、QA、OPS/SEC 按影响范围完成评估。
3. PO 决定批准、拒绝或延期；涉及发布门禁降低时 QA/OPS 具有否决权，涉及安全例外时 SEC 具有否决权。
4. 批准后更新 `scope.md`、相关 ADR、风险登记表、里程碑和需求追踪矩阵。
5. 变更实现必须带测试、迁移和回滚证据。
6. 验收后关闭变更单，并保留历史记录。

## 4. 紧急安全修正

正在被利用的高危安全问题可先止血，但只能采取最小必要改动。24 小时内补交变更单、风险更新、测试证据和事后复盘。安全修正不得顺带加入无关功能。

## 5. 不需要变更单的事项

- 不改变行为的重命名、格式化和内部重构。
- 补充已有规则的测试和文档错字修正。
- 在既定范围内修复明确违反本 P0 基线的实现。

如无法判断是否改变行为，默认需要变更单。
